## Verdict

ABSENT, and for once "absent" is the correct end state, not a backlog item: the template scaffolds a JSON-API **service** on the appkit preset spine (health dashboard, error pages, drain, sd_notify, env legs), while cqrs-htmx scaffolds a server-rendered **web app** (HTMX/Datastar UI, event-sourced usermgmt with WebAuthn/OAuth2/TOTP, admin panel, login page, one-call full-stack setup). Importing any of its 15 modules into a domainless service would pull Casbin, SQL drivers, templ-components and an auth domain the archetype has no call sites for. This is a routing problem, not a wiring problem, and the expensive mistake it must prevent is an adopter cloning the wrong template: a web-app team starting here hand-rolls usermgmt/admin/auth for weeks; a service team starting at cqrs-htmx's `setup.New()` inherits an app framework it must then strip. The template currently prevents that mistake **by accident**: the ruling that names the correct relationship ("a NEW Go HTTP service starts on the go-appkit preset spine; the cqrs-htmx Path-A shape composes ON TOP, `RunWithAppkit` (setup/v4) is the canonical wiring", owner ruling 2026-11-21) is recorded in cqrs-htmx's SKILL.md:134 ("FLEET DEFAULT, owner ruling 2026-11-21") and go-appkit's AGENTS.md:24, documents a template adopter has no reason to open on day one. Three sentences in the README close the gap (see Gaps 1–3, all docs-only). Nothing should be wired.

The wrapper the template uses (`go-appkit/cqrs` → `system.New`) is bypassed entirely.
  2. **go-appkit does not depend on cqrs-htmx.** The only require is the test-only integration consumer: `/home/lars/projects/go-appkit/integration/go.mod:6` pins root `v4.15.0` (latest is v4.19.0, their train to ride); appkit's root `.golangci.yml` depguard **bans** `cqrs-htmx/setup` imports repo-wide ("makes the direction invariant mechanical"), and `go.work` excludes it to avoid a false cycle. Direction: setup → appkit core, never the reverse (appkit AGENTS.md:24).
  3. **The bridge is real, published, and canonical: `setup.RunWithAppkit`.** `setup/v4` (the one-call composition root for the whole web-app family) directly requires appkit core and composes the full cqrs-htmx bundle (domain middleware, mounting, projection-aware readiness) onto an `appkit.Service` instead of `httputil.Server`, with verified timeout/SSE-drain/health equivalences (`/home/lars/projects/cqrs-htmx/setup/run_appkit.go:13-41`, adopted from the lib's ADR-001 uplift; stable since 2026-09-07 per appkit AGENTS.md:24). This is the exact shape the fleet ruling blesses for "service spine + web app in one binary".
  4. **Both stacks converge at `system.New` through two different wrappers.** The template's sanctioned event path is `go-appkit/cqrs` → `cqrs.NewEventService` → `system.New` (verified in the go-cqrs-lite review, appkit eventservice.go:447). cqrs-htmx's equivalent for the usermgmt domain is `systemadapter`, "wires usermgmt deciders/projections into `system.New()`; dispatch happens in the system, not here" (`/home/lars/projects/cqrs-htmx/systemadapter/go.mod:2`, presets at systemadapter/presets.go:35+; requires metaengine v4.26.0 + sqliteengine v4.9.1). So event-sourced consumers of either stack share the same journal/projection core; the wrappers differ because the domains differ (empty service skeleton vs usermgmt aggregate family). Note: `setup/v4` itself still composes `usermgmt` via the storage/v4+watermill+projectionhost path (setup/go.mod:19-28), not systemadapter; systemadapter is the adopter-side alternative used by crm/sperrmuell-direct-class apps.
  5. **Shared foundations make the two stacks mixable without tax collisions:** cqrs-htmx root and appkit both sit on `httputil` (v1.9.0 there, v1.8.0 in the template graph), `go-error-family` v0.12.0, `go-sse`, `go-etag`, and go-cqrs-lite ids/events: one error taxonomy and one SSE wire format across both.

## Gaps and opportunities

1. **Add a "Service or web app?" routing box to the README.** [TEMPLATE, docs-only] Impact: high (wrong-template is the multi-week mistake). Ease: trivial. What to say, in substance: this template scaffolds a JSON-API service on the appkit preset spine. If the project is a server-rendered web app needing users/login/admin (HTMX or Datastar UI), do NOT start here: start from cqrs-htmx (`github.com/larsartmann/cqrs-htmx/v4`, MIT): Path A (root `App` only) for CQRS+HTMX endpoints, `setup.New()`/`examples/admin-demo` for the full users+admin stack. One paragraph + link; no code. Placement: README "Start" section, before the rename steps, because it filters before the clone.
2. **Document the sanctioned grow path (the ruling's second half).** [TEMPLATE, docs-only] Impact: medium-high. Ease: trivial. A service cloned from this template that later grows a CQRS/HTMX or user-facing surface composes cqrs-htmx ON TOP of the preset spine: `setup/v4`'s `RunWithAppkit` serves the bundle through the same appkit Service lifecycle (graceful drain, readiness, sd_notify) the template already ships (evidence: `setup/run_appkit.go:13-41`; ruling recorded 2026-11-21 at cqrs-htmx SKILL.md:134 and appkit AGENTS.md:24). Natural home: one row in FEATURES.md ("Grow path: web-app surface → compose cqrs-htmx via setup.RunWithAppkit, see README") plus the README box from gap 1; the events skeleton comment (`internal/events/events.go`) may cross-reference it so the two event paths (appkit/cqrs for the service's own domain; systemadapter for usermgmt) are never conflated.
3. **Record the two-archetype boundary in AGENTS.md.** [TEMPLATE, docs-only] Impact: medium. Ease: trivial. One line: this repo's go.mod must never require cqrs-htmx: web-app composition happens in derived services, not the archetype (mirrors appkit's depguard direction invariant). Keeps future AI sessions from "helpfully" wiring the framework in, which is the only realistic way this report's findings could rot.
4. **[LIB-UPSTREAM, minor] The preset README does not carry the spine-first variant the ruling cites.** cqrs-htmx's SKILL.md claims "the appkit preset/README shows the spine-first variant", verified absent: `grep -ci 'cqrs-htmx' /home/lars/projects/go-appkit/preset/README.md` = 0 (checked 2026-11-23; its "spine" mentions are all the appkit spine itself). ## Should the archetype adopt or wire more?

No, and unlike most rows in this corpus, "no" is the fully correct answer rather than a deferral. The honest routing for an adopter starting from this template, verified against the repos:

- **(a) Adopt cqrs-htmx INSTEAD: right call, wrong template.** If the project is a web app with users/admin/auth, starting here means hand-rolling event-sourced usermgmt, session middleware, CSRF/HTMX plumbing and an admin surface that cqrs-htmx ships tested (Playwright 245/245 both engines, WebAuthn via CDP virtual authenticator). The template's job is to say so early (gap 1), a README pointer, never code.
- **(b) Grow INTO cqrs-htmx from this template: feasible and sanctioned, with one seam to know.** The stacks are not rivals: shared foundations (httputil, go-error-family, go-sse, go-cqrs-lite ids/events) and the published `setup.RunWithAppkit` bridge mean a preset-spine service can mount the cqrs-htmx bundle under the same appkit lifecycle the template already ships. The seam: the two event paths are separate wrappers over the same `system.New`; a service using the skeleton's `go-appkit/cqrs` EventService for its own domain, then adding cqrs-htmx usermgmt, gets usermgmt's storage/v4+watermill wiring (or systemadapter) beside it; both journal into go-cqrs-lite but through separately-configured hosts. That is a deliberate composition decision for the adopting service, not something the archetype should pre-wire, which is exactly why gap 2 documents it instead of coding it.
- **(c) Never mix at the archetype level.** The template must stay cqrs-htmx-free (gap 3): every module it pulled in would land in every cloned service's graph, and the preset spine already owns every concern the two stacks share (health, drain, error pages, SSE hub, security headers).

What belongs in the default binary: nothing (current, correct). What belongs in docs/scaffold: the routing box and grow-path rows (gaps 1–3). What must stay out: every cqrs-htmx module, without exception.

## Risks

- The one real risk is routing, not code: an adopter who needs a web app and starts from this template has no in-repo signal redirecting them (gap 1); the cost surfaces weeks later as hand-rolled auth. Conversely, a team that starts at cqrs-htmx for a plain JSON service inherits an app framework; less costly, but the same signpost answers it.
- Grow-path seam risk (adopters only): two event wrappers over one `system.New` core (appkit/cqrs vs usermgmt/systemadapter) can be conflated into one host by a well-meaning refactor; the composition decision belongs to the adopting service and should be made once, deliberately (see "Should the archetype adopt", point b).
- v5 cutover (adopters only): the tree is already SSE-only and v5 deletes the deprecated re-export aliases; the codemod mitigates, but anyone pinning v4 today should budget the migration. Nested-import security lag is documented upstream with a recipe (oauth2/v4.13.1 precedent); a grow-path adopter's audit should re-check sub-tag coverage, not just root.
- Doc-truth risk (small, cross-repo): the SKILL.md claim that the appkit preset README shows the spine-first variant is currently false (gap 4): the routing ruling is one stale sentence away from being undiscoverable everywhere except AGENTS files.
- No security issues in what the template actually links: nothing. License compatibility is unproblematic in the only direction that can occur (adopting MIT cqrs-htmx into a PROPRIETARY derived service is fine; the reverse never arises).
