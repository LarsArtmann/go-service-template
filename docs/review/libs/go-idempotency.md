## Verdict

Not used at all, and that is mostly the correct posture for this repo today: the template has no mutating endpoint, no command dispatch, and both go-appkit and go-cqrs-lite explicitly keep idempotency consumer-owned (appkit `cqrs/commands.go:20-22`, `cqrs/eventservice.go:457-461`). The module sits in `go.mod` line 103 as a v0.3.2 indirect pulled by `go-appkit/cqrs v0.9.0`, and it is not even compiled into the default binary (`go list -deps ./...` shows no idempotency package); it only compiles under `-tags events` via cqrs-lite's middleware package, inert. "Max" here is not wiring code, it is two things: (1) version hygiene, where this is the largest gap in the whole audit (v0.4.0, v0.5.0, v0.6.0 all shipped since the pin), and the fix belongs to appkit/cqrs's go.mod, not the template; and (2) a near-zero-cost docs breadcrumb so the adopter who adds their first POST finds `middleware.HTTP`, the response-replay recipe, and `idemtest` instead of reinventing dedup.

## Gaps and opportunities

1. **G1: Version drift, the largest in the audit (v0.3.2 vs v0.6.0), and it is not the template's pin to move** `[PRESET-UPSTREAM]`. The template resolves v0.3.2 because `go-appkit/cqrs@v0.9.0` itself requires `go-idempotency v0.3.2 // indirect` (go-appkit/cqrs/go.mod:64; unchanged at latest tag cqrs/v0.10.0 and at HEAD 74e4d80, while cqrs-lite middleware/v4@v4.7.2 only pulls v0.3.1). The gap contains three minors, all additive, none breaking: v0.4.0 permanent claims (`Forever`, ADR-006) plus corrected backend-adapter guidance (the documented PostgreSQL `CheckAndRecord` previously reported a duplicate on every first claim, CHANGELOG [0.4.0] Fixed); v0.5.0 the `idemtest` consumer test kit as a separate nested module (idemtest/v0.1.0); v0.6.0 `WithClock` injectable clock. Upgrade path, in train order: (1) go-cqrs-lite tags middleware/v4 (and system/v4, commandlifecycle/v4) past their current tags, since HEAD go.mods already require v0.6.0 but the latest middleware tag v4.7.2 still requires v0.3.1 (`git show middleware/v4.7.2:middleware/go.mod`), and completes the deferred Forever-to-DedupStore propagation (go-idempotency TODO_LIST.md: "Propagate Forever to go-cqrs-lite ... consume go-idempotency@v0.6.0, deferred 2026-11-17"); (2) go-appkit/cqrs bumps those requires and re-tidies its stale indirect line; (3) the template bumps `go-appkit/cqrs v0.9.0` to the next release and the graph resolves v0.6.0 with zero template code changes. Impact: high (fleet-wide currency; the template cannot get there alone). Ease: medium (two upstream releases). No existing appkit train carries it: preset v0.1.1 does not even require appkit/cqrs; the template reaches it only through its own direct `go-appkit/cqrs` require (go.mod line 8, serving the events skeleton).
2. **G2: No adopter breadcrumb for idempotent POST/PUT (the HTTP-side story)** `[TEMPLATE]`. The lib ships a stdlib-only `middleware.HTTP` honoring `Idempotency-Key` (middleware/http.go:30, 400 missing key / 409 duplicate / 503 store failure, fail-closed) plus the response-replay recipe for Stripe-style replay semantics (doc.go:347) and the `idemtest` HTTP drills to test it (idemtest/http.go). The template does nothing instead: internal/api/routes.go demonstrates only `GET /api/status` and no doc mentions idempotency. Impact: medium (the first adopter POST is exactly when at-most-once matters, and this is the lib's only surface for non-CQRS services). Ease: high (docs-only). Sketch (a short docs section, no code):
   ```go
   // documented recipe for adopters adding their first POST:
   handler := idemhttp.HTTP(myDurableStore, 24*time.Hour,
       httpx.ResultHandler(createOrder)) // wrap only idempotency-contract routes
   // test it: idemtest.Send / RequireDuplicate / RequireExecutions (idemtest/v0.1.1)
   ```
   Deliberately NOT wired as code: see "Should the archetype adopt or wire more?".
3. **G3: Events skeleton does not point at the engine-backed dedup route** `[TEMPLATE]`. Under `-tags events` the skeleton opens a sqlite-backed event system (internal/events/events.go, `DSN: "events.db"`), and the sanctioned dedup path on that stack is `system.Dedup()` over a `metaengine.DedupStore` engine (go-cqrs-lite/system/v4/dedup.go:33; README "On the go-cqrs-lite stack?" points cqrs-lite consumers there instead of hand-written backends). A one-line comment in the skeleton naming that route (and cqrs-lite's `middleware.CommandIdempotency`) costs nothing and matches the skeleton's documented-purpose posture. Impact: medium for event-legged adopters. Ease: high (one comment).
4. **G4: Forcing the bump locally in the template** `[NOT-NOW + reason: the template does not require this module directly, nothing it builds compiles it under default tags, and an MVS force-bump (`go get go-idempotency@v0.6.0`) would add a fake require line while leaving the real stale pin (appkit/cqrs) as fleet debt; it buys zero runtime benefit today]**. Wait for the appkit/cqrs train from G1.

## Should the archetype adopt or wire more?

No code adoption in the default binary, and that is the honest answer. Wiring `middleware.HTTP` onto the current API layer would be an actively wrong demo: the adapter 400s any request without an `Idempotency-Key` header (middleware/http.go:33-37), which would break the template's GET-only example endpoints, and there is no Store to give it: the lib ships none by design (ADR-001), the only in-tree store is the deprecated process-local `MemoryStore`, and a durable backend choice (Redis vs SQL vs engine) is exactly the adopter-specific decision an archetype must not make for its cloners. Both frameworks above this lib already made the same call: appkit's default command chain excludes idempotency "deliberately" (commands.go:20-22) and its event service defers to the consumer appending `middleware.CommandIdempotency` over "their own durable store" (eventservice.go:457-461). What belongs in the template is the breadcrumb, not the behavior: a short docs section (G2) covering `middleware.HTTP`, the response-replay recipe, TTL-sizing guidance, and `idemtest`, plus the one-line pointer in the events skeleton (G3). A build-tag-gated `internal/httpidempotency` skeleton modeled on internal/events would carry weight without a legitimate store to demonstrate, so it stays out; the build-tag-gate tool remains right for framework-weight legs, wrong for a 3-line middleware whose missing piece is an adopter-owned backend. The collective-improvement routing: the durable implementations live in cqrs-lite engines (metaengine.DedupStore, ADR-0142/0158, where its own idempotency/{kvstore,sqlstore} modules were retired in their favor), the contract and test kit stay in this lib (LIB-UPSTREAM), and if HTTP-side demand ever materializes across non-CQRS services, the wiring surface belongs in go-appkit (preset/httpx opt-in leg with an injected Store, PRESET-UPSTREAM), not per-project. The lib's own fleet evidence says that demand is not there yet: 0 of 10 consumers import `middleware/` (ROADMAP.md:19, YAGNI gate re-confirmed 2026-11-17).

## Version currency

Pin v0.3.2 indirect vs latest v0.6.0: three minors behind, every one of them shipped 2026-11-17 (v0.3.2 is from 2026-11-03). Contents of the gap, from the CHANGELOG: **v0.4.0** permanent claims `idempotency.Forever` (never expires, never upgraded/downgraded by later Records, five new contract invariants) and backend-docs correctness (the documented PostgreSQL `CheckAndRecord` had reported `ErrDuplicate` on every first claim; the backend-primitive tables moved from `ON CONFLICT DO NOTHING` to reclaimable conditional upserts). **v0.5.0** the `idemtest` consumer test kit (contract-certified test store, failure injection, recorder spy, execution counters, dispatch drills, in-process HTTP drills, sabotage-proven) shipped as a separate nested module tagged idemtest/v0.1.0. **v0.6.0** `WithClock` option making `NewMemoryStore` expiry deterministic (variadic options, existing call sites compile unchanged). No API breaks across the three minors; no new storage backends (the no-backends stance is permanent); the semantics additions are additive (Forever is a new sentinel TTL; empty-string key and `ttl <= 0` behavior unchanged). The template is missing, concretely: permanent-claim semantics, the whole consumer test kit, and deterministic-clock testing. Whose move: NOT the template's (indirect, via go-appkit/cqrs v0.9.0, whose go.mod carries the winning v0.3.2 edge). It does not ride an already-released appkit train: appkit cqrs/v0.10.0 still pins v0.3.2. cqrs-lite is already at v0.6.0 at HEAD in middleware/v4, system/v4, integration/v4, idempotency/sqlstore/v4 (unreleased at the middleware tag level: latest middleware tag v4.7.2 requires v0.3.1), so the sequence is cqrs-lite tags, then appkit/cqrs bumps, then the template's one-line `go-appkit/cqrs` bump rides it. At lib HEAD (8fd593e, 5 commits past idemtest/v0.1.1): the pinned-clock drill `RequireAllowsAfterExpiryPinned` and `PinnedClock` (shipped as idemtest/v0.1.1), `FuzzClockJumps`, the in-window assert in `RequireAllowsAfterExpiry`, `SendConcurrently` request options, nested-module CI coverage; root-package API is unchanged since v0.6.0, so the unreleased delta is idemtest-side and CI/docs only.

## Risks

Nothing active: no template or appkit code path executes this library, so there is no misuse surface in the default binary (verified: `go build ./...` clean, `go list -deps ./...` contains no idempotency package). Drift-adjacent and future-adopter footguns, all verified in source: (1) adopters consulting the pinned v0.3.2 copy of the package docs get the pre-v0.4 backend-adapter guidance with the PostgreSQL first-claim false-duplicate bug (CHANGELOG [0.4.0] Fixed), a real hazard only if someone copies the old documented adapter rather than implementing fresh; (2) `middleware.HTTP` requires the header and 400s without it (middleware/http.go:33-37): it must wrap only idempotency-contract routes, and keys are taken verbatim so shared stores need per-route namespacing (http.go:27-29); (3) cqrs-lite's `NewIdempotency` silently passes through an empty key (middleware/v4/idempotency.go:32-34), so a key extractor returning "" disables dedup without error; (4) a store error must fail closed, never process (README "Common pitfalls"; cqrs-lite wraps non-sentinel errors as Transient, idempotency.go:41-46); (5) TTL must be sized to the retry horizon, not the request timeout, and a crashed claim poisons the key until TTL (no `Delete`; deferred per ADR-004); (6) never compute `now.Add(Forever)` (UnixNano overflows 2262; store a permanent representation instead, store.go:56-61); (7) `MemoryStore` is deprecated and lint-forbidden outside tests, so no template example should ever use it. Sole runtime dependency is go-error-family v0.12.0 (already in the template graph at the same version).
