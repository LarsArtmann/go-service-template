## Verdict

Not used at all, and that is correct for this repo. go-credentials-store is not a thin "OS keyring wrapper" (my pre-read assumption, refuted on opening the repo): it is a full product, an event-sourced encrypted-at-rest store for API keys, Playwright session blobs (storageState), and passwords, built on the go-cqrs-lite system composition root, with a single-operator admin UI (list/filter/SSE live updates, audited one-time reveal, audit trail, /status, /metrics) mountable as one handler via `adminui.Mount` (`adminui/adminui.go:45`). README's own framing: "Embedded Go library first" with the admin UI as convenience (`README.md:8-9`), "Feature-complete for single-operator use" (`README.md:18`). For this template the answer to the security-posture crux is blunt: an HTTP service archetype does NOT need a credentials store, because its secrets arrive at deploy time through env/file config (`internal/app/service.go:32-33` env tags, `:40` config.Load with flag > env > file > default; `SECURITY.md:41` no secret is committed), and a service that writes secrets it was handed inverts that posture: it adds a master-key bootstrap problem (the store itself boots from `CREDENTIALS_MASTER_KEY_V1` env or a 0600 key file), an sqlite event store on disk, and an admin surface that must be defended. "Max" here means: keep the default binary free of it (achieved), keep it out of the preset (achieved, and correct: upstream itself declares multi-tenancy/OIDC/central-service OUT_OF_SCOPE, `FEATURES.md:58`), and add one docs pointer routing the minority of adopters whose service genuinely banks credentials to the proven fleet pattern (the single small miss). The adopter story is real but narrow, see below: all three fleet consumers are personal-infra services that persist third-party credentials; cqrs-htmx, the service shape with the strongest OAuth-token argument, uses neither this library nor any token persistence at all.

## Gaps and opportunities

Ranked by impact x ease (highest first).

1. **Adopter-routing docs pointer** [TEMPLATE]. What the lib offers: a pkg.go.dev-indexed, production-adopted store with two proven integration shapes: embed-and-mount (CV: `adminui.Mount` behind an operator guard at `/admin/credentials`, `CV/internal/features/credentials/handlers/credentials_admin_handler.go:20`) and resolve-with-fallback (bank-sync: `internal/credentials/resolver.go:43-63`, store-first with env fallback, loud on real store failures). What the template does instead: nothing; no doc mentions credentials, so an adopter whose service starts banking OAuth tokens or sessions discovers the library by luck. Impact: low-to-moderate (3 of ~40 fleet repos hit this need, but for those it is the difference between a sealed audited store and a plaintext file); ease: trivial. Sketch, one paragraph in `docs/DOMAIN_LANGUAGE.md` or the README config section: "Deploy-time secrets arrive via env/file (config.Load precedence flag > env > file > default). If your service OBTAINS secrets at runtime it must persist (OAuth refresh tokens, browser sessions, third-party API keys), do not write them to disk yourself: adopt github.com/larsartmann/go-credentials-store, copy bank-sync's ResolveAPIKeyWithFallback seam for env-fallback cutover, and mount its admin UI behind your operator auth if you need one."
2. **Keep the store out of the skeleton: the archetype answer to the security-posture crux** [NOT-NOW + wrong shape for an archetype + weight]. (a) An HTTP service archetype does not need a credentials store: its secrets arrive at deploy time (env/flag/file, `internal/app/service.go:40`; `SECURITY.md:41`), and "no hardcoded secrets" doctrine is already satisfied without any storage. A store the service writes to INVERTS the posture: it needs a master key at boot (from env, so you trade N env secrets for 1 env master key plus a DB plus rotation ops), it persists sensitive state the archetype otherwise never has, and it drags a second deployment grammar (cqrs.yaml + sqlite state dir). (b) The adopter story where a service writes credentials is real but narrow, and the fleet evidence is unambiguous: CV (web app; provider API keys + login session blobs; store seam ON BY DEFAULT per owner ruling 2026-11-06, `CV/internal/credentials/store.go:19-20`), bank-sync (personal bank-sync daemon; provider API keys via fallback seam, `bank-sync/internal/credentials/resolver.go:13`), profileagent (freelance-platform automation; login-session custody with adminui mounted, `profileagent/internal/composition/custody_store.go:63`). All three are single-operator personal-infra services banking third-party credentials; none is a generic CRUD service. The sharpest test case, cqrs-htmx (OAuth2 login via usermgmt), uses neither the library nor any token persistence: its go.mod has no dependency (verified, zero matches) and `rg 'refresh_token|RefreshToken|StoreToken'` over its Go sources matches nothing, because its oauth2 provider exchanges codes against config-supplied ClientID/ClientSecret and keeps no refresh-token store (`cqrs-htmx/usermgmt/oauth2/provider.go`). (c) Routing if the story fires for a given adopter: adopter-local, by cloning the bank-sync seam pattern from the docs pointer in gap 1. Not the preset: a preset leg would push go-cqrs-lite encryption, prometheus client_golang, an sqlite state dir, and an admin surface into every adopter's runtime for a minority need, and upstream has explicitly ruled the multi-operator generalization OUT_OF_SCOPE (FEATURES.md:58, revisit triggers "UI leaves localhost, second human" in ROADMAP). Not the skeleton, not even build-tag-gated: unlike `internal/events` (a 40-line wrapper over a preset leg whose whole tree is already in the graph), a credentials skeleton is a product decision with key bootstrap and auth guard; the build-tag tool is for wiring weight, not for making product choices on the adopter's behalf.
3. **If service-side demand ever becomes common: interface convention, not wiring** [NOT-NOW now; PRESET-UPSTREAM only on real demand]. If multiple preset-spawned services start needing store-first resolution, the right collective move is a documented resolver-interface convention in go-appkit (the shape bank-sync already invented locally: `APIKeyResolver` interface satisfied by `*credentials.Resolver`, `bank-sync/internal/credentials/resolver.go:33-35`), so services code against the interface and boot it only when configured. That keeps the preset free of the dependency while making every adopter's seam identical. Demand today: zero preset-spawned services; revisit when the first one banks credentials.
4. **Lib-side CHANGELOG [Unreleased] hygiene** [LIB-UPSTREAM]. The lib's CHANGELOG `[Unreleased]` block still lists the templ v0.3.1100 + templ-components v1.27.0 coordinated wave as changed (`CHANGELOG.md:25-29`) even though the `[0.4.3]` section (2026-11-13, `CHANGELOG.md:5-10`) shipped exactly that wave with commit 7812a3e; meanwhile the genuinely unreleased work (the settle-tolerant point-Get below) is recorded nowhere in the CHANGELOG. Release intent lives in that section per the fleet's own convention, so the drift is worth one small doc pass at the lib: fold the stale entry into 0.4.3 and record the settle window under Unreleased. Impact: trivial for this template (nothing is pinned), meaningful for the three tag-pinning consumers reading release intent.

## Should the archetype adopt or wire more?

No. Default binary: nothing, unchanged; the archetype's security posture is complete without it (env/file config in, no secrets out, nothing at rest). Docs/examples: the single credential-routing paragraph from gap 1 is the entire warranted footprint, and it belongs next to the config story because the honest answer to "where do my service's secrets live?" is "they arrive via env/file at deploy time; only store one if your service OBTAINS secrets at runtime, and then use the fleet store". Must stay out: any skeleton wiring (including build-tag-gated: a credentials skeleton wires a product, not a preset leg, see gap 2), any preset ask. The build-tag-gate pattern (`internal/events`) is the right tool only on the day the preset grows an optional credentials leg, which should itself wait for real demand from preset-spawned services (currently zero). Where go-credentials-store belongs in the fleet stack: exactly where its three consumers already sit, personal-infrastructure services that bank third-party credentials, with bank-sync's fallback seam as the canonical first-90-minutes adoption shape and CV's guarded mount as the canonical full-admin shape.

## Risks

For the template itself: none, nothing is imported (verified across go.mod, go.sum, and all Go sources). What the gap-1 docs pointer should carry so adopters do not misuse it:

- Single-operator by design: multi-tenancy/OIDC/central-service are OUT_OF_SCOPE upstream (FEATURES.md:58; ROADMAP G1/G3 revisit triggers: UI leaves localhost, second human). Mounting adminui on a multi-user service without an operator guard is the headline misuse; README itself says the host owns authorization (`README.md:76`), and CV's mount sits behind its operator session plus OriginCheck.
- Master-key bootstrap: the store refuses to boot without key material (`options.go:17` comment); non-loopback binds REQUIRE an API key (README:27). An adopter must plan env (or 0600 key file) for the master key and the rotation runbook (`scripts/rekey.sh`, live v1->v2 rotation documented in docs/operations/key-management.md).
- Weight: 37 direct requires (22 LarsArtmann-family), including the go-cqrs-lite system stack, encryption/v4, prometheus client_golang, templ-components; the runtime footprint includes an sqlite state dir with WAL files. Moderate incremental graph cost for a cqrs-leg service, but real operational state where the archetype has none.
- Fallback doctrine: bank-sync's seam encodes the fleet incident lesson, store failures other than ErrUnconfigured must surface as loud Infrastructure errors, never silent env degrade (`bank-sync/internal/credentials/resolver.go:40-42`); an adopter copying the pattern must copy that clause.
- Freshness verdicts are manual-only by upstream verdict (ROADMAP open question, verdict 2026-10-29): "fresh" means operator-verified recency, not auto-probed; do not read freshness as automated validation.
- Upstream release mechanics: GitHub Actions is dark by decision (billing), local buildflow gates are canonical, and a consumer-simulation gate runs pre-tag (CHANGELOG 0.4.2); consumer compatibility is deliberately guarded, so tag pins are low-risk. CHANGELOG [Unreleased] staleness is a doc nit (gap 4), not a code risk.
