00Summary

The archetype's shape is superb: the composition root is byte-for-byte the preset's documented canonical pattern, the default binary carries zero event-sourcing weight (verified with go list -deps), the spine's production surface was live-verified end to end, and all five absent libraries are absent for the right reasons. "To the max" is gated upstream, not locally: the go-appkit preset under-exposes its own legs (no dashboard, health, middleware, or hub option passthrough), several fleet libs sit graph-only, and the appkit refresh train is due. The template owes documentation and two small tests, not re-architecture.

The bottom line Do not re-integrate libraries template-locally. Route the work where every fleet consumer benefits: two bug fixes and the option passthroughs belong in go-appkit and its libs, the pin refresh is one stamped train, and the template's own share is docs plus a POST example and two tests.

01Findings

Ordered by impact. Each finding names the routing the audits gave it: fix it in the library, in the go-appkit preset, in this template, or deliberately not now.

Blocking · silent security degrade

APPKIT_SECURITY=strict via env silently degrades to the standard profile

go-appkit preset/preset.go:95-99 + preset/security.go:24-32 · contradicts preset README:44-45

resolveLegs records strict, but applySecurity receives cfg.Security, which is nil when the leg is env-driven; securityMiddlewares(nil) then defaults the profile to Standard. No OriginCheck, no boot rejection, and no test pins the env-strict path end to end. An operator who flips the documented env var believes they are in strict mode and are not.

Fix [LIB-UPSTREAM] Thread the resolved profile into applySecurity and add an env-strict integration test. Cross-file: go-appkit.md Gaps #1.
Blocking · boot panic on a documented opt-out

NoDashboard=true panics inside preset.New at the current module resolution

go-health handlers.go:160 (unstamped-probe guard) via appkit health/mount.go:122,105 · empirically reproduced

The appkit health module floors go-health at v0.8.1 while the template's graph resolves v0.10.0 (MVS). At v0.10.0 the probe handler guards against unstamped probes and panics; at the floored v0.8.1 the same code boots fine. The dashboard opt-out, a documented posture, is therefore broken by pure version skew.

Fix [PRESET-UPSTREAM] Bump appkit health's go-health floor to v0.10.0; harden the guard in go-health to error instead of panic. Cross-file: go-health.md.
Important · silent degradation on by default

Default WriteTimeout cuts every SSE stream at 30 seconds, including the always-on dashboard

internal/app/service.go leaves Timeouts zero · go-appkit health/doc.go:124-129 documents the dashboard cut as “degrades but works”

Verified independently from three sides (go-appkit, go-sse, go-health): the dashboard's /health/sse stream dies at 30.007s and APPKIT_REALTIME=on produces /events streams that die the same way. Heartbeats reset proxy timers, not http.Server deadlines. go-sse itself documents nothing about write deadlines, so the trap is invisible in everything the library ships.

Fix [PRESET-UPSTREAM] + [LIB-UPSTREAM] The preset applies its NoTimeout sentinel for SSE-serving routes (or documents the pairing in the env grammar); go-sse adds a “server requirements” note.
Important · due maintenance

The appkit refresh train is due: core v0.13.0 and cqrs v0.10.0 shipped after the stamp

AGENTS.md version stamp pins core v0.12.0 / cqrs v0.9.0 · latest tags v0.13.0 / v0.10.0 (2026-11-22)

The gap contains real fixes: the sqliteengine EnforceCap journal-writer deadlock with per-connection busy_timeout, SSE malformed Last-Event-ID now returning 400 instead of hanging, a RawQuery decoder crash-loop fix, and the system.Standard topology. The bump is MVS-clean (cqrs v0.10.0 has zero appkit requires; core v0.13.0 is additive) and is the template's own pin to move, in one stamped ritual: pins, AGENTS.md stamp table, dogfood probe.

Fix [TEMPLATE] One refresh ritual; the ten other drifted pins (see the refresh train table) ride their owners' next releases.
Important · third-party code at runtime

The dashboard serves CDN assets while embedded assets sit linked but unserved

go-health-dashboard view.templ:122,125-141 · embedded SDK linked via handlers.go:359 but /health/datastar.js 404s

Runtime-verified: /health loads Tailwind from cdn.tailwindcss.com (the Play CDN, a development tool) and Datastar 1.0.3 from jsdelivr via a deprecated alias, while the embedded Datastar 1.0.4 bytes are already linked into the binary. The preset passes zero dashboard options, so WithEmbeddedDatastarSDK and WithCSSPath are unreachable. This is CSP-hostile and leaks a runtime dependency on two CDNs.

Fix [PRESET-UPSTREAM] + [LIB-UPSTREAM] Preset passes the dashboard options; go-health-dashboard embeds a compiled baseline stylesheet and an ETag'd SDK handler. Cross-file: go-datastar.md gap 1, go-health-dashboard.md.
Important · lost machine-readability

go-error-family BSD exit codes never reach os.Exit

cmdguard cli_errors_json.go:39-53 duck-types its own ExitCoder · go-error-family error.go:324 returns 0 when unset

The whole error story is built on classified errors (family + code, machine-readable), and the chain is superb through HTTP rendering. But cmdguard never imports the lib: family exit codes (EX_DATAERR 65, EX_NOHOST 68, EX_SOFTWARE 70, EX_TEMPFAIL 75) are lost, and cmdguard's machine-readable error hints come from its own sentinel table instead of the family taxonomy. Systemd units and wrappers read exit codes, not stderr.

Fix [LIB-UPSTREAM] A thin seam (adapter or shared interface) so family-bearing errors map to their BSD codes at the CLI boundary. Cross-file: go-error-family.md gap G1.
Nice to have · first impression

The pretty 404 ships as an unstyled fragment

appkit errorpages.go:175 calls WriteNotFound404 · templ-components errorpage/handler.go:318-347 ships no CSS even on the document path

Runtime-verified: the 404 is a bare main fragment with Tailwind classes but no doctype, charset, viewport, or stylesheet. The template's own landing page advertises pretty error pages; what adopters actually serve is unstyled. The lib should embed a compiled baseline stylesheet so every fleet consumer benefits without a Tailwind pipeline.

Fix [LIB-UPSTREAM] Mirror the layout/embed.go htmx.min.js precedent. Cross-file: templ-components.md top gap.
Nice to have · one-liners

Two one-line preset fixes: the dashboard Version card and criticality

preset/preset.go:109 omits health.WithVersion(cfg.Version) · zero health.Option passthrough blocks WithCriticalServices

The dashboard's Version stat card renders “unknown” although the template ldflags-stamps Version and the preset Config carries it. And because the preset passes no health options, readiness can never flip 503 on a failing dependency: every check is warn-only. Both unlock with a single options field on preset.Config.

Fix [PRESET-UPSTREAM] One WithVersion call now; one HealthOptions (and DashboardOptions) passthrough field. Cross-file: go-health-dashboard.md, go-health.md.
Nice to have · teaching posture

The example API demonstrates only a GET; the blessed POST path exists unwalked

internal/api/routes.go:25 · httpx ResultHandlerWithValidation (bind.go:58) unused anywhere in the template

Every adopter writes request bodies. The framework's decode path (1 MiB cap, bind.* Rejection codes, Validator hook) is exactly what the archetype should teach, and the same is true of a classified 404 producer: routes_test.go tests neither the rendered error shape nor the describe contract, and the cmdguard audit found zero CLI tests.

Fix [TEMPLATE] One POST example handler, one rendered-error-shape test, one testutil.AssertDescribeContract test. Cross-file: go-codec.md #1, go-error-family.md #2, cmdguard.md gaps.
Nice to have · signposts

Adopter routing exists only in tribal knowledge

README / FEATURES / DOMAIN_LANGUAGE · zero mentions of cqrs-htmx, business-rules, credentials-store, daemon, filewatcher

The 2026-11-21 owner ruling (new service on the preset spine, cqrs-htmx composes on top via setup.RunWithAppkit) lives in no README on either side of the bridge. A web-app team cloning this template finds no signpost, and the same is true for the four correctly-absent libraries whose adopter stories are real but undocumented.

Fix [TEMPLATE, docs-only] A “Service or web app?” routing box in the README, one adopter-routing line per absent lib, and the events skeleton comment drift fixed while there. Cross-file: cqrs-htmx.md, go-business-rules.md, go-credentials-store.md, go-daemon.md, go-filewatcher.md.

03Absent-library verdicts

Five libraries are not in the module graph at all. Each audit asked whether that is an oversight or a decision; all five are decisions, recorded here so the next session does not re-derive them.

Library Verdict Why Template action
go-business-rules DO NOT ADOPT Severity-aware validation framework for domain types; a domainless archetype must not pre-decide where validation lives. Seven fleet consumers use it adopter-locally, the correct home. One docs pointer

05Method and verification

Twenty-one parallel deep-dive audits, one per library, each against the library's local checkout at HEAD (2026-11-23) and the template's single module. Shared brief, shared schema, shared scoring rubric: count inventory rows N, drop Not-applicable rows to get A, score Fully leveraged 1 / Partially used 0.5 / Missed or Misused 0, and the adoption score is round(100 × Σ / A). Bands: very high 85+, high 70-84, moderate 50-69, low below 50. Every N/A row carries a reason; a claim without a file:line citation is marked UNVERIFIED or absent.

Gates the series passed before shipping: structure check (nine schema headings per report), score reconciliation (every claimed score re-derived from its inventory table; three drifts found and fixed), and command replay (294 verify commands executed, the remaining expected-empty greps and runtime probes verified by their auditors). The working tree stayed green throughout: one leaked scratch file from a replayed heredoc was removed and go build plus go vet pass.
